# 17 排错工作法：把红色报告变成可解释的问题

> 本章目标：学会分类失败、最小化复现和保持原始证据。测试工程师需要调查，不只是重跑。

## 17.1 先问失败发生在哪一层

测试失败有多种来源：业务违反预期、测试预期写错、定位/解析实现错误、环境不可用、数据污染、时序竞争、清理失败。相同 TimeoutException 可能对应元素改名，也可能对应服务没响应。相同 500 可能是接口约定中的预期，也可能是异常服务故障。

第一步看失败方法是否为 setup/测试体/teardown；第二步看最早的有意义异常及 cause/suppressed；第三步看截图、响应、SQLSTATE；第四步核对输入和环境；最后才提出修复。日志从最后一行往上猜往往只看到 Maven 的总括错误。

## 17.2 五个具体排错案例

**案例 A：Web 登录超时。** 先看截图是在登录页、错误页还是空白。若错误区域显示密码不对，检查 -Dusername/-Dpassword 和演示账户状态；若用户名框定位不到，核对 DOM 与定位器；若没有截图，检查 driver 是否创建成功。不要一开始把 waitSeconds 改成 120。

**案例 B：排序测试失败。** 若是等待超时，检查下拉框选中值与实际列表；若断言价格不一致，看元素价格解析、商品变化和排序方向；若只并行失败，检查是否共享会话或页面状态。当前预期依赖演示目录，合法目录变更也可能影响断言。

**案例 C：API JSON 解析失败。** 先看状态码与 Content-Type，确认是否 HTML 代理错误。再看 base URL、请求 Accept、响应 body。不要为了让解析成功随便删掉 contentType 验证，也不要把真实凭据全量打印进日志。

**案例 D：数据库 cannot connect。** 先确认 Docker 引擎，再看 compose ps 的健康状态、端口和 DB_*。若能连但表不存在，检查数据卷是否为预期 fixture。删除数据卷不是第一个诊断步骤。

**案例 E：断言通过但构建失败。** 检查 API cleanupApi、数据库 rollback/close、浏览器 quit。失败可能在后置阶段。把 teardown 改成 catch 后空处理会隐藏问题，不是修复。

## 17.3 最小复现，但不破坏隔离

可以先选分组，再选单类，必要时单方法。单独运行仍应自行准备数据，这是隔离设计的检验。不要把同一失败重复几十次直到有一次绿，再只保留绿灯。

```powershell
# 不需要数据库的 Web 单类
.\mvnw.cmd '-Dtest=LoginTest' '-Dheadless=true' test
# API 分组
.\mvnw.cmd '-Dgroups=api' test
# 数据库分组，先准备 fixture
docker compose -f docker/docker-compose.yml up -d --wait
.\mvnw.cmd '-Dgroups=database' test
```

注意显式 -Dtest 是选择测试的另一条入口，不等于仍按完整 suite 跑；诊断探针就是通过它选择。使用不同结果目录避免诊断结果混入最终业务报告。

## 17.4 Flaky test 不是错误的借口

Flaky 指相同相关条件下结果不稳定。但要确认条件真的相同：公开服务重置、网络抖动、浏览器版本变化、数据冲突都可能是环境变化。把所有偶发红灯叫 flaky 然后重试会失去调查机会。

项目没有自动重试失败测试。重试可以作为调查手段，记录每次结果和时间，而不是把失败从报告抹掉。修复等待、隔离和环境前提后，再用有针对性的重复运行确认问题缓解。

## 17.5 写一个可操作的缺陷报告

教学模板：标题描述行为差异；环境说明浏览器/模式/版本；前置数据说明可复现输入；步骤最小化；Expected 明确依据；Actual 描述实际；Evidence 附截图/响应/日志；Impact 说明用户影响。不要只贴 Java 堆栈让别人猜你做了什么。

例如：“在包含背包和车灯的购物车中删除背包后，车灯也消失。预期保留车灯且 badge=1；实际购物车为空。”这比“CartTest failed”有价值。还应确认不是当前测试选错按钮，否则应修测试而不是报产品缺陷。

## 17.6 修改测试前做一次反例检查

修改 expected 之前先问：需求是否真的改变？删除断言之前先问：它原本保护哪个风险？增加 sleep 之前先问：应该等待哪个可观察条件？引入共享状态之前先问：单独运行与并行是否仍可靠？

维护测试不是让它永远绿，而是让它对真实错误敏感、对合理变化可解释。一个有明确原因的失败比一个什么也证明不了的绿灯更有用。

<details><summary>自测：测试在 CI 失败、本地通过，是否说明 CI 配置一定错了？</summary>

不是。可能是无头模式、Linux 字体/布局、网络、浏览器版本、资源竞争、时序或本地残留状态差异。先复现对应模式，比较环境与证据，再定位具体差异。CI 与本地谁都不是天然正确答案。

</details>

**English checkpoint:** “I classify the failure, inspect the earliest meaningful evidence, and reproduce it in the smallest isolated scope before changing the test.”
