# 02 测试思想：从执行动作到建立证据

> 本章目标：理解 test oracle、正反向测试、状态变化、隔离和覆盖边界。读完要能设计测试，不只是解释现有代码。

## 2.1 测试是一条可以被推翻的判断

一句需求“合法用户可以登录”仍然太宽。测试需要具体条件：使用标准演示用户，输入正确密码，点击登录。预期也要可观察：到达商品页并显示 Products 标题。如果实际没发生，测试必须失败。没有明确失败条件的脚本可能只是演示。

**Test oracle（测试判定依据）**是你决定正确与否的依据。来源可以是需求、协议、已知 fixture、独立计算或者状态不变量。`assertEquals` 只是执行比较的工具，真正关键的是 expected 从哪里来。

例如订单总额的 expected 如果直接调用同一个 `checkout.total()` 获得，再和 `checkout.total()` 比较，永远很难发现问题。测试重复了读取，没有建立独立依据。本项目将 total 与 subtotal + tax 比较，提供了关系约束；同时核对商品已知价格，避免所有显示金额一起错而仍保持相加关系。

但当前代码没有独立税率规则。tax 非负、总额等于小计加税，只能证明显示金额之间一致，不能证明法定税率或四舍五入规则正确。**断言强度决定结论强度。**

## 2.2 Arrange / Act / Assert，以及 Cleanup

AAA 是阅读测试的方法：Arrange 准备条件，Act 触发行为，Assert 核对结果。很多自动化还需要第四步 Cleanup。

用 `orderStatusCanBeUpdated` 举例：先创建 pending 订单（Arrange），执行 UPDATE 设置 paid（Act），确认影响一行且 SELECT 得到 paid（Assert），测试后 rollback（Cleanup）。一个测试中可以有多个相关断言，只要它们围绕同一个行为。不是每个测试只能写一个 assert。

框架把部分准备与清理放进基类，因此单看测试体可能误以为“这个浏览器从哪里来的”。读代码时必须把 `@BeforeMethod` 和 `@AfterMethod` 补回执行链。

```text
建立可控起点 → 触发一个业务变化 → 从外部读取结果 → 与独立依据比较 → 恢复状态
     Arrange            Act               Observe / Assert             Cleanup
```

## 2.3 正向与反向，不是成功测试与失败测试

Positive test 验证被允许的行为能完成，例如正确密码登录。Negative test 验证被禁止的行为被正确拒绝，例如没有 Token 不能修改预约。

“无 Token 返回 403”是预期结果，所以测试应通过。故意调用 `fail()` 的探针才会造成预期的测试失败。不要把“接口返回错误”和“测试结果失败”混成一件事。

反向测试有两个重要维度：**拒绝的解释**和**状态没有被非法推进**。LoginTest 同时核对错误文案与仍在登录页。API 无认证修改同时核对 403 和随后 GET 的内容未变。只断言错误信息不足以排除“系统报错了但偷偷修改了数据”。

## 2.4 等价类、边界与组合

Equivalence partitioning（等价类划分）把输入分成行为相近的类别。登录的正确密码、错误密码、空密码属于不同类别；锁定用户又体现账户状态维度。一个随机字符串不比十个随机字符串天然弱，关键看它们是否触发同类行为。

Boundary value analysis（边界值分析）关注范围交界，例如长度 0、1、最大允许值、超过最大值。当前结账测试覆盖空值，但没有覆盖长度上限、Unicode、空格、邮编格式等完整边界。不要给已有 DataProvider 贴上“全边界覆盖”的标签。

组合爆炸也很真实：用户名状态 × 密码状态 × 浏览器 × 网络状态会迅速膨胀。测试设计需要按风险选场景。支付金额错误风险通常高于按钮颜色差异；本项目选择登录、购物车、结账、授权和数据完整性，是合理的入门重点，却不是生产测试计划全集。

## 2.5 状态转换与不变量

State transition 是系统从一个状态到另一个状态。购物车为空 → 添加 A → 包含 A → 添加 B → 包含 A/B → 删除 A → 只剩 B。测试最后一步时不能只断言 A 消失，还要断言 B 存活，否则“删除全部”也会伪装成成功。

Invariant（不变量）是在操作前后应该保持的性质。排序可以改变顺序，却不应增减商品；PATCH 可以改变指定字段，却应保留其他字段；非法修改应保持整个原对象不变。项目里最值得学习的断言，往往就是这些“变化了什么、没变化什么”的组合。

## 2.6 隔离与可重复性

Isolation 指一条测试不依赖另一条测试留下的状态，也不应该破坏别人的状态。浏览器每次新建会话；API 使用 UUID 数据并记录自己的 ID；数据库每次独立事务并回滚。三种方式分别针对三种系统能力。

Repeatability 不是保证公共互联网永远稳定，而是在相同前提下可以重复运行，不需要人工清理上一轮残留。若测试 B 只有在测试 A 先跑过才成功，B 的前置条件藏在了执行顺序里。单独运行、分组和并行都会暴露这种问题。

UUID 解决名称碰撞概率，不解决全世界并发冲突；ThreadLocal 解决线程中的引用隔离，不解决数据库脏数据。选择隔离机制时先问“共享的到底是什么”。

## 2.7 回归、冒烟与覆盖率

Regression testing 检查已有行为没有被改坏；Smoke testing 用少量关键路径快速判断环境和核心功能是否值得继续测。它们是执行目的与选择范围，不是两种编程语言。一个用例可以同时属于 smoke 和 regression。

当前 smoke 为 9 个，跨 Web/API/DB。运行完整 smoke 需要数据库；只运行 Web 的 parallel-web profile 再选 smoke，则只包含 Web smoke。分组是集合，不是互斥文件夹。

46 是场景执行数量，不是代码覆盖率百分比。没有被测应用源码和覆盖率采集，就不能从用例数推导覆盖率。更有意义的讨论是“哪些需求、状态、风险有证据，哪些还没有”。

## 2.8 Unit、Integration、End-to-End 如何区分

测试层级关注测试边界，不由所用断言库决定。Unit test 通常把一个较小逻辑单元置于受控环境中，尽量不依赖真实浏览器、网络或数据库；Integration test 检查多个组件协作；End-to-End test 从使用者或外部入口穿过一段真实系统流程。团队命名有差异，说明实际边界比争论标签更重要。

本项目没有被测业务应用的单元测试。Selenium 结账覆盖演示 Web 用户流程；REST Assured 测外部 HTTP 接口；JDBC 测真实 PostgreSQL fixture。这些不是因为用了 TestNG 就变成 unit tests。TestNG 可以运行多种层级，它是执行工具。

Testing pyramid（测试金字塔）表达一种反馈成本思路：通常用较多快速、局部检查覆盖逻辑，再用较少较慢的跨组件/用户流程验证关键组合。它不是要求每个项目按固定百分比凑数量。本仓库无法修改第三方应用源码，因此不能拿 24 Web、14 API、8 DB 的比例判断第三方系统是否遵循金字塔。

Mock 用可控替身替代依赖，便于模拟异常和缩小边界；真实依赖能提供更多集成证据，却更受环境影响。当前项目使用真实浏览器、公共 API 和本地数据库，没有引入 Mock 服务。不能声称已经覆盖网络超时、服务器限流等所有异常，只因为客户端设置了超时。

## 2.9 哪些工作值得自动化

重复、规则明确、需要频繁回归且可以稳定观察的行为适合自动化。探索陌生功能、判断复杂用户体验、分析需求歧义仍需要人的调查。自动化执行固定检查，不会自动发现你从未想到的风险。

例如本项目可以反复核对结账错误文案，但“这段错误文案对真实用户是否清楚”仍需要产品语境。探索式测试可以发现遗漏场景，再把有价值、可重复的场景转成自动化。手工和自动化不是互相淘汰的关系。

成本不仅是写第一版，还包括准备数据、维护选择器、排查误报和更新契约。抽象层要服务维护，不要为一次简单调用引入很多没有实际用途的接口。当前客户端返回 Response、页面对象返回业务观察值，是在复用与可读性间选择有限封装。

## 2.10 误报与漏报：把方向说清楚

把“测试报告失败但产品行为实际正确”称为误报时，例如定位器过时或等待过早，团队会浪费调查时间。把“产品确有缺陷但测试仍通过”称为漏报时，例如只检查 badge 数量却不查商品身份，团队得到错误信心。不同语境对 positive 一词有不同约定，所以面试最好先说明你指的是哪种现象。

修误报不能以增加漏报为代价。删除 assert 或捕获异常不处理，可能让红灯消失，却把检测能力也删了。好的修复应保留风险检查，同时纠正选择器、同步或测试数据前提。

拿到一个测试后，试着构造最小错误实现：登录永远成功、删除清空全部、PATCH 清空未指定字段、UPDATE 返回 200 但不改数据。若它仍会绿，就知道下一条有意义的断言应放在哪里。这种反例思考比一味增加执行次数更接近测试设计。

<details><summary>自测：删除后 GET 返回 404，但删除请求返回了不符合约定的状态码，测试应不应该通过？</summary>

如果你同时验证接口契约和最终行为，应失败。状态码本身也是对调用者的约定。项目会检查 DELETE 为 201，再检查 GET 为 404。生产设计可能选其他成功码，但必须根据被测系统约定制定断言，不能只要数据消失就接受任何响应。
