# 16 GitHub Actions：把本地命令变成自动工作流

> 本章目标：读懂 YAML、job/step/matrix、失败后产物和 CI 的真实验收状态。

## 16.1 CI 的核心是可重复执行

Continuous Integration 让提交或 PR 触发一套自动检查，减少“只有某个人电脑能运行”的依赖。它不会自动写出更好的测试；弱断言放到云端仍然弱。这个项目的 workflow 负责准备环境、执行现有测试并保存证据，没有部署产品，所以不能只凭存在 YAML 就说完成持续部署 CD。

当前目录没有 Git 仓库与远端，V5 工作流经过 actionlint 静态检查，尚未在 GitHub 真实运行。这是重要事实，后续上传仓库后才可补真实运行记录。教材保留这个未完成的外部验收项，不伪造绿灯截图。

## 16.2 先读骨架

{{source:.github/workflows/qa-tests.yml}}

YAML 通过缩进表达层级。`jobs` 下是两个 job 定义 web/backend；matrix 展开后实际为 Chrome、Firefox、API、database 四个 job。`steps` 是每个 job 内顺序执行的步骤。没有 needs 依赖，所以这四个 job 可以独立调度，不保证先 API 再 DB。

`uses` 调用已有 Action，例如 checkout 获取仓库、setup-java 准备 Java、upload-artifact 上传文件。`run` 执行 shell 命令。`${{ matrix.browser }}` 是 GitHub 表达式，由工作流展开成 chrome 或 firefox，不是 Java 字符串语法。

## 16.3 为什么 runner 与本地不同

runs-on=ubuntu-24.04 表示选择 GitHub 托管 Linux 环境。本地是 Windows，所以调用包装器使用 `sh ./mvnw`，而不是 mvnw.cmd。-B 是 Maven batch 模式，适合非交互日志。Java 21 与本地验收环境大版本一致，pom 仍以 release 17 编译。

cache:maven 缓存依赖，减少重复下载；它不是缓存测试成功结果。每次命令仍执行测试。跨浏览器 matrix 则用同一源代码分别验证环境兼容性。

## 16.4 fail-fast=false 与 always() 是不同层次

fail-fast=false 让一个 matrix job 失败时，不立即因为该失败取消其他 matrix 工作，便于同时得到多个环境的结果。它不把失败变成功。

默认情况下，后续步骤通常以之前步骤成功为前提。报告和上传加 if:always()，使测试失败后仍尝试保留证据。它也不是绝对保证：机器不可用、强制取消或上传服务错误时产物仍可能缺失。准确说法是“配置为失败后仍尝试生成和上传”。

没有 continue-on-error，也没有在测试命令后用忽略退出码把结果变绿。这保证业务测试失败会反映到 job 结果。

## 16.5 数据库只在需要的 job 启动

backend matrix 为 api/database。条件 `matrix.group == 'database'` 让 PostgreSQL 只在数据库 job 启动。--wait 与 --wait-timeout 120 给数据库准备时间，然后运行分组。最后无论测试结果都尝试日志收集与 down。

这是四个独立环境，不是一个 job 启动数据库给其他 job 共享。跨 job 不会自动共享 localhost 或容器，因此这样的条件安排很关键。

## 16.6 Artifact 是结果证据，不能替代源码

每个 job 上传 Surefire、Allure 原始结果与 HTML；Web 上传截图，DB 上传 postgres.log。名字带浏览器/分组，避免不同 job 产物混淆。retention-days=14 是保留期，过期后不能假设还可下载。

审查一次真实 CI 至少看：触发的提交、测试选取是否正确、执行数、通过/失败/跳过、错误堆栈、对应附件、清理结果。没有执行到测试却上传一个旧报告也不能算成功；clean test 与独立 runner 有助于避免混入旧结果，但仍需核对日志。

## 16.7 面试中怎样准确描述

现阶段说“我实现了 GitHub Actions 的四个 matrix job，并完成静态校验；本地相应测试已通过，云端运行待仓库发布后验证。”当真实运行成功后，再更新为有证据的说法。

不要说“支持 Jenkins、移动端 CI、部署流水线”，这些没有实现。能清楚说出边界，往往比堆术语更能证明你理解自己的工程。
